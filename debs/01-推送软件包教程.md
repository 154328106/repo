# 推送 DEB 到“无言以对”软件源

这份教程只讲如何把已经检查好的 `.deb` 提交到 GitHub 软件源，不讲如何修改包内信息。修改名称、版本、作者和描述等内容，请看 [02-修改DEB普通信息教程.md](02-修改DEB普通信息教程.md)。

## 最简单的方法：双击 BAT

日常使用时，直接双击本目录中的：

```text
一键推送插件.bat
```

然后按提示操作：

1. 输入存放插件的本地目录，或直接把文件夹拖进窗口；
2. 按编号选择一个或多个 `.deb`，输入 `A` 可以全选；
3. 为每个软件包选择 `依赖插件`、`美化插件` 或 `功能插件`；
4. 核对准备上传的文件和分类；
5. 输入提交说明，直接回车会自动生成；
6. 脚本自动提交并推送到 `main`；
7. 如果电脑有 GitHub CLI，脚本会继续等待 Actions 构建完成并显示结果。

也可以把一个文件夹直接拖到 `一键推送插件.bat` 上，脚本会把它作为待选择目录。

脚本只会暂存你明确选择的 DEB 和分类配置，不会执行 `git add .`。分类写入 `config/sections.tsv`，Actions 只覆盖在线 `Packages` 索引中的 `Section`，不会拆包或修改原始 DEB。如果发现已有暂存内容、同名文件内容不同、文件超过 GitHub 上限或 Actions 构建失败，脚本会停止并显示原因。

下面的手动步骤用于了解脚本实际做了什么，或者在脚本无法运行时备用。

## 一、推送前必须确认

准备推送的软件包应当满足：

- 确实适用于 Relaxin / RootHide；
- 架构是 `iphoneos-arm64e`，纯主题素材也可以是 `all`；
- 文件能够正常安装，不是损坏的备份包；
- 作者或许可证允许你重新分发；
- 不上传付费包、破解包、账户授权文件或来历不明的系统组件。

特别注意：不要覆盖已经发布的同版本软件包。只要包内内容发生变化，就应当提高 `Version`，否则手机端可能继续使用缓存中的旧文件。

## 二、把 DEB 放入正确目录

目标目录是：

```text
D:\Claude\My project\repo\debs
```

可以直接通过资源管理器把 `.deb` 复制进来。建议文件名采用：

```text
软件包ID_版本号_架构.deb
```

例如：

```text
zhuti.example.mask_1.0-roothide_iphoneos-arm64e.deb
```

文件名主要方便自己管理，真正决定软件包身份的是包内 `DEBIAN/control` 中的 `Package`、`Version` 和 `Architecture`。

## 三、打开仓库并同步远端

打开 PowerShell，执行：

```powershell
Set-Location 'D:\Claude\My project\repo'
git pull --ff-only origin main
```

如果 `git pull` 报告本地修改冲突，不要执行 `git reset --hard`，也不要随便删除文件。先运行：

```powershell
git status --short
```

看清楚哪些是自己的本地文件，再处理冲突。

## 四、确认这次准备上传的文件

执行：

```powershell
git status --short
```

常见状态：

- `??`：新文件，还没有被 Git 跟踪；
- `M`：已经跟踪的文件被修改；
- `A`：文件已经放入本次暂存区；
- `D`：文件被删除。

只上传自己这次明确要发布的 DEB。不要使用 `git add .`，因为它可能把其他测试包、字体包或私人文件一起提交。

## 五、只暂存指定的 DEB

把下面文件名替换成实际文件名：

```powershell
git add -- 'debs/zhuti.example.mask_1.0-roothide_iphoneos-arm64e.deb'
```

然后检查：

```powershell
git status --short
git diff --cached --stat
```

确认目标 DEB 前面是 `A` 或 `M`，并且暂存区里没有其他不相关文件。

如果误把某个文件放进暂存区，可以取消暂存，不会删除本地文件：

```powershell
git restore --staged -- 'debs/误添加的文件.deb'
```

## 六、创建提交

提交说明尽量写清楚加入了什么：

```powershell
git commit -m 'Add example RootHide theme'
```

提交后再检查一次：

```powershell
git status --short
```

存在其他未跟踪文件并不代表提交失败；只要它们没有被暂存，就不会被推送。需要确认本次提交具体包含什么时，执行：

```powershell
git show --stat --oneline HEAD
```

## 七、推送到 GitHub

执行：

```powershell
git push origin main
```

推送成功后，GitHub Actions 会自动：

1. 检查每一个 DEB 是否能被正常读取；
2. 检查架构是否为 `iphoneos-arm64e` 或 `all`；
3. 检查是否存在重复的 `Package + Version + Architecture`；
4. 重新生成 `Packages`、`Packages.gz`、`Packages.xz` 和 `Release`；
5. 发布到 GitHub Pages 软件源。

## 八、检查自动构建

如果电脑已经安装并登录 GitHub CLI，可以执行：

```powershell
gh run list --workflow publish.yml --limit 3
```

看到刚才的任务后，可以把任务编号替换到下面命令中：

```powershell
gh run watch 任务编号 --exit-status
```

显示 `completed` 和 `success` 才表示部署成功。也可以打开仓库网页中的 **Actions** 页面查看。

构建失败时不要反复推送同一个文件。打开失败任务，查看 `Validate packages and build indexes` 那一步的报错。常见原因包括：

- DEB 损坏；
- 架构不是 `iphoneos-arm64e` 或 `all`；
- 仓库中已有相同的 `Package + Version + Architecture`；
- 包内 `control` 缺少 `Package`、`Version` 或 `Architecture`。

## 九、检查在线源是否已经收录

源地址：

```text
https://154328106.github.io/repo/
```

可以在 PowerShell 中按软件包 ID 查询在线索引：

```powershell
curl.exe -L 'https://154328106.github.io/repo/Packages' |
    Select-String 'Package: zhuti.example.mask'
```

能够看到对应的 `Package:` 行，说明在线索引已经收录。手机端随后在 Sileo 中刷新“无言以对”源；如果暂时看不到，等待几十秒后再次刷新。

## 十、以后更新同一个软件包

更新时遵守以下规则：

1. 先修改包内 `Version`；
2. 重新打包，并让文件名也体现新版本；
3. 新旧版本可以同时保留，仓库支持多版本；
4. 如果确定不再提供旧版，可以通过 `git rm -- 'debs/旧文件.deb'` 删除旧版；
5. 提交、推送，再确认 Actions 成功。

不要在没有提高版本号的情况下替换同一个 DEB，否则 APT 客户端和 CDN 缓存可能让不同用户拿到不同内容。

## 常用检查命令

```powershell
Set-Location 'D:\Claude\My project\repo'
git status --short
git log -5 --oneline
git show --stat --oneline HEAD
git remote -v
```

这几条都是只读检查，不会修改或删除文件。
